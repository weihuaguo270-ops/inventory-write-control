# 库存受控写入（inventory-write-control）范围说明

> 立项文档。范围已于 2026-11-15 **书面冻结**；业务实现从 S1 起按刀推进。  
> 截止：2026-11-15（Asia/Shanghai）。作者：郭伟华；仓库账号：`weihuaguo270-ops`。

## 1. 产品是谁用、解决什么

| 项 | 说明 |
|---|---|
| 产品名 | 库存受控写入（inventory-write-control） |
| 使用者 | 需要并发预占库存、商家改价/改库存、以及模型草案经人工审批后写入的交易/运营侧系统 |
| 核心问题 | 同一 SKU 并发预占不超卖、扣减幂等；改价/改库存先过可写死规则，再经指纹审批才写库 |
| 不是什么 | 不是电商全站；不是客服/审核台；不是通用 Agent 框架；不是 change-delivery 的延续 |

与工作助手（`react-agent`）的关系：**并列独立产品**。工作助手偏业务办理；本项目偏并发、幂等与受控生产写入。如需对齐，**只复用契约与语义**，不迁代码、不搬循环、不合并仓库。

## 2. 主路径（唯一主线）

### 2.1 预占路径

```text
下单请求（带幂等键）
  → 对同一 SKU 预占（Redis 热库存原子扣减 + PostgreSQL 事务/行锁落账）
  → 超时未支付：释放预占
  → 支付成功事件：确认占用
```

硬约束：

- 同一幂等键重复请求：不得重复扣减。
- 可售不足：必须挡住，不得超卖。
- 超时释放与支付确认均须幂等（订单号或请求号）。

### 2.2 改价 / 改库存路径

```text
改价或改可售库存请求（含生效时间）
  → 规则检查（上限、生效窗口、同 SKU 冲突、不得把已预占库存改没）
  → 模型可出草案（销量/活动说明），但不得直接写库
  → 人工审批钉死方案指纹（商品、数量、价格、生效时间等）
  → 指纹校验通过后才更新可售库存或价目
```

硬约束：

- 审批通过后不得改计划再写入；指纹不一致一律拒绝。
- 模型输出只到草案；写入只走 Go 受控接口。

### 2.3 出错代价（必须挡住）

- 超卖
- 错价上架
- 把已预占的货改没

## 3. 技术栈（已拍板）

| 层 | 选型 | 用途 |
|---|---|---|
| 写入服务 | Go（单服务，先不做微服务） | 预占、确认、释放、幂等写入接口 |
| 数据库 | PostgreSQL | 库存、预占单、审批记录；事务或行锁防超卖 |
| 缓存 | Redis | 热库存原子扣减、幂等键去重 |
| 消息队列 | **仅** Apache RocketMQ | 支付成功、超时取消等事件；消费必须幂等 |
| Agent | 独立 Python Agent | 出草案 + 审批闸门；通过接口把钉死方案交给 Go |
| 配置 | 环境变量 | 不引入服务网格、多种队列或全套可观测平台 |

明确禁止同时接入 Kafka / NATS / RabbitMQ；不用 Go 重写 Agent 循环。

## 4. 数据对象（最小集合）

| 对象 | 关键字段（口径） | 说明 |
|---|---|---|
| SKU 库存 | `sku_id`, `sellable_qty`, `reserved_qty`, `version` | 可售与已预占分离；写库需防并发 |
| 价目 | `sku_id`, `price`, `effective_at`, `expires_at?` | 改价带生效窗口 |
| 预占单 | `reservation_id`, `order_id`, `sku_id`, `qty`, `status`, `idempotency_key`, `expire_at` | 状态：`reserved` / `confirmed` / `released` |
| 审批记录 | `approval_id`, `plan_fingerprint`, `payload_snapshot`, `status`, `decided_by`, `decided_at` | 指纹钉死方案；通过后按快照写 |
| 写入请求日志 | `request_id` / 幂等键, `result` | 支撑幂等与审计 |

状态机（预占单）：

```text
reserved ──支付确认──▶ confirmed
    │
    └──超时/取消──▶ released
```

`confirmed` 与 `released` 为终态；重复事件不得回滚已确认占用，也不得二次释放造成负预占。

## 5. 接口（口径，非实现）

Go 服务对外最小面：

| 接口 | 职责 | 幂等键 |
|---|---|---|
| `POST /reservations` | 预占 | 请求幂等键（如 `Idempotency-Key`） |
| `POST /reservations/{id}/confirm` | 确认占用（也可由支付成功事件触发） | 订单号或请求号 |
| `POST /reservations/{id}/release` | 释放预占（也可由超时取消事件触发） | 订单号或请求号 |
| `POST /catalog/price-changes` | 提交改价（规则检查 → 待审或直接拒绝） | 请求号 |
| `POST /catalog/stock-changes` | 提交改可售库存 | 请求号 |
| `POST /approvals/{id}/decide` | 人工通过/拒绝；通过后按钉死指纹写入 | 审批决定请求号 |
| `GET /skus/{id}` | 查询可售/预占/当前价（演示与验收用） | — |

事件（RocketMQ，模拟即可）：

| 事件 | 消费动作 |
|---|---|
| `payment.succeeded` | 幂等确认预占 |
| `order.timeout_cancelled` | 幂等释放预占 |

Python Agent 边界：

- 输入：销量或活动说明等只读上下文。
- 输出：改价/补货**草案** + 待审方案指纹材料。
- **不得**持有数据库写权限；写库只调用上述 Go 接口，且须已过审批闸门。

## 6. 规则检查（可写死）

改价 / 改库存在进入审批或写入前必须执行：

1. **上限**：价格、可售增量/绝对值不超过配置上限。
2. **生效窗口**：`effective_at` 落在允许区间；过期或倒挂窗口拒绝。
3. **同 SKU 冲突**：同一 SKU 已有未决或重叠生效的变更则拒绝或排队（首版：直接拒绝冲突）。
4. **预占保护**：新可售不得低于当前 `reserved_qty`（不能把已预占的货改没）。
5. **指纹一致**：审批通过后的写入载荷必须与 `plan_fingerprint` 对应快照一致，否则拒绝。

## 7. 方案指纹

指纹至少覆盖：

- `sku_id`
- 变更类型（改价 / 改库存）
- 目标数量或目标价格
- `effective_at`（及若有的失效时间）
- 其它写入必需字段的规范化序列

计算：对规范化后的方案做哈希（如 SHA-256），写入审批记录。  
批后若任一字段变化 → 指纹不符 → **拒绝写入**，须重新提交与审批。

## 8. 非目标（立项即冻结）

- 不复制开源电商/库存产品，不整仓搬运或改名
- 不做内容/广告审核台，不做通用客服/工单台
- 不做完整支付系统、完整电商前台；支付成功与超时取消用事件模拟
- 不把 `change-delivery`（Issue → 影子执行 → `plan_sha256` 审批 → Draft PR）继续铺成 P2/Go 主线
- 不从 `weihuaguo270-ops/react-agent` 迁代码；不搬 Agent 循环与仓库结构
- `react-agent`、`llm-eval-engine`、`trace-debugger` 保持独立，不与本项目合并
- 不做微服务拆分、服务网格、多队列并存、全套可观测平台
- 已冻结范围外的能力不提前实现（S2/S3 另开刀）

## 10. 验收口径（S1）

S1 过关至少要能演示：

1. 同一 SKU、库存 N，并发 M 次预占（M > N）→ 成功数 ≤ N，无超卖。
2. 同一幂等键重放 → 只扣一次。
3. 超时取消事件 → 预占释放，可售恢复。
4. 支付成功事件 → 预占确认；重复投递不二次扣减。

口径细则见 [S1-SLICE.md](S1-SLICE.md)。
